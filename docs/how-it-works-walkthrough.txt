================================================================================
  COMPLIANCE-RAG: HOW THE WHOLE THING WORKS
  A plain-English walkthrough of every file in the project
================================================================================

This file is written for someone who wants to understand WHY the code does
what it does, not just WHAT it does. Read it top-to-bottom and you'll know
the project end-to-end.


--------------------------------------------------------------------------------
PART 1. THE BIG IDEA
--------------------------------------------------------------------------------

We are building a small assistant for compliance officers at law firms.
They have a folder of policy documents (AML / KYC rules). They want to ask
a question in plain English and get back:

  - A short answer
  - The exact paragraphs from the policies that the answer is based on
  - Proof that the AI did not make anything up

This is called RAG: Retrieval-Augmented Generation.
The recipe has two halves:

  1. RETRIEVAL: find the most relevant pieces of text from the policies.
  2. GENERATION: ask an LLM (a large language model) to answer using only
     those pieces of text.

We never let the LLM answer from its own memory. We feed it the policy
text and force it to ground its answer in what we gave it. That way the
answer is auditable: a human can always look back and check exactly
which paragraphs the AI used.

The project is a command-line tool with two commands:

  python main.py ingest --docs ./policies
        Reads the policies, breaks them into chunks, turns each chunk into
        a vector (a list of numbers), and saves everything to disk.

  python main.py query --question "..." --k 3
        Takes a question, finds the top 3 most relevant chunks, sends them
        plus the question to the LLM, validates the LLM's reply, and prints
        a JSON answer to the screen. Also writes one line to audit.log.


--------------------------------------------------------------------------------
PART 2. THE WHOLE FLOW IN ONE PICTURE
--------------------------------------------------------------------------------

INGEST FLOW (run once, takes ~30 seconds):

   policies/*.md
        |
        v
   [chunker.py]   split each policy into small pieces by section header
        |
        v
   [embedder.py]  turn each piece into a 384-number vector (its "meaning")
        |
        v
   [vector_store.py]  save the vectors + chunk text to ./data/

QUERY FLOW (run every time the user asks something):

   user question
        |
        v
   [embedder.py]   turn the question into a 384-number vector
        |
        v
   [retriever.py]  find the chunks whose vectors are closest to the question
                   AND the chunks whose words match the question (BM25)
                   fuse both lists, keep the top 3
        |
        v
   [prompts.py]    build a message: "Here are 3 chunks. Here is the question.
                   Answer using only the chunks. Return JSON."
        |
        v
   [llm.py]        send that message to Groq's Llama 3.3 70B
        |
        v
   [query.py]      validate the LLM's JSON. If it broke, retry once with a
                   stricter "fix your JSON" prompt. Throw away any chunk IDs
                   the LLM made up. Build the final response.
        |
        v
   [audit.py]      write one line to audit.log with everything that happened
        |
        v
   stdout          print the final JSON object

PART 3. FILE-BY-FILE WALKTHROUGH (src/ folder)
--------------------------------------------------------------------------------

Files are explained in the order they get used, NOT alphabetical order.


================================================================================
src/schemas.py    "The shapes of our data"
================================================================================

WHAT IT DOES
------------
Defines the shape of every piece of data that moves through the system,
using Pydantic. Pydantic is a library that lets us say "this thing must
have these fields, and field X must be a string" - and it will yell at us
if it isn't.

THE CLASSES
-----------
- Chunk: one piece of policy text. Has chunk_id (a number), document
  (file name), section (heading text), text (the actual policy text).

- RetrievedChunk: a Chunk plus a score saying how relevant it was.

- Citation: what we show the user as proof. Just the document name and
  the chunk text.

- QueryResponse: the JSON we print to the screen at the end. The brief
  tells us exactly what fields this needs: question, answer, citations,
  model, latency_ms, timestamp, error.

- LLMAnswer: what we expect BACK from the LLM. The LLM returns two
  things: the answer text, and a list of chunk IDs it used. This is a
  KEY trick (explained more in DR-4 of the README).

- AuditEntry: what we write to audit.log. Includes everything: question,
  response, the exact chunks we showed the LLM, model name, latency,
  timestamp.

WHY WE NEED THIS
----------------
Two reasons.

First, the brief explicitly requires us to validate LLM output against a
schema. If the LLM returns garbage that doesn't fit, we must catch that
and handle it cleanly. Pydantic does this automatically.

Second, when the same data shape is used in many places, defining it in
one file means we can never accidentally use different field names in
different places. Change it here, every file that uses it gets updated.


================================================================================
src/config.py    "Where settings come from"
================================================================================

WHAT IT DOES
------------
Reads the .env file and turns it into a Python object we can use.

THE LOGIC
---------
We use pydantic-settings. It looks at the .env file, finds variables like
GROQ_API_KEY=..., and sets matching fields on the Settings class.

If a variable isn't in .env, we use a default value. For example,
embedding_model defaults to "BAAI/bge-small-en-v1.5". So the user only
HAS to set GROQ_API_KEY; everything else has sensible defaults.

WHY IT MATTERS
--------------
- API keys must never be in code (security). Reading from .env is the
  standard way.
- The .env file is in .gitignore, so it never gets pushed to GitHub.
- One single object (Settings) is passed around. If we need a new
  setting tomorrow, we add it here once.


================================================================================
src/chunker.py    "Breaking policies into bite-size pieces"
================================================================================

WHAT IT DOES
------------
Takes a markdown file like "01_customer_due_diligence_policy.md" and
splits it into many small chunks. Each chunk is one section of the
policy (like "Section 3.1 Employment / Salary").

WHY WE CHUNK AT ALL
-------------------
Two reasons we can't just dump a whole policy into the LLM:

1. The embedding model (BGE) can only handle about 512 tokens at a time.
   A whole policy is way bigger.

2. Even if it could, we want PRECISE retrieval. If we asked "what
   documents do I need for employment income?" we want to get back that
   ONE specific paragraph, not 5 pages of unrelated rules.

THE LOGIC, STEP BY STEP
-----------------------
1. Read the markdown file as a big string.

2. Find every "## " heading using a regular expression. These are the
   section headers like "## 3. Documentation Requirements by Category".

3. Take the text between one ## heading and the next - that's one
   section. We make that into one Chunk.

4. CHECK: is this section too long? Some sections (like "## 3.
   Documentation Requirements by Category" with 565 words) are bigger
   than what BGE can handle. If so:
       a. Try to split on "### " subheadings (like ### 3.1, ### 3.2).
       b. If there are no subheadings, split on paragraph breaks with a
          small overlap (60 words). The overlap means we don't accidentally
          cut a sentence in half between two chunks.

5. For every chunk, we PREPEND a header line:
       "Document: 02_source_of_wealth.md | Section: 3. Documentation..."
   This is important: when we later show the chunk to the LLM, the LLM
   sees where the text came from, so it can cite it correctly.

6. Number every chunk with a unique ID (0, 1, 2, ...). This ID is how
   we later check which chunks the LLM actually used.

WHY THIS APPROACH (NOT FIXED-SIZE CHUNKS)
-----------------------------------------
Many tutorials say "just split every 500 characters." That's a bad idea
here. The test questions reference policies BY SECTION ("Policy 02,
Section 3.1"). If we cut mid-section, the chunk is ugly: half a sentence
of one rule, half a sentence of the next. The LLM gets confused and the
citation makes no sense.

Section-aware chunking means each chunk is a self-contained rule. A
citation IS the rule. Clean, auditable, easy to verify.

RESULT
------
On the provided 5 policies, this produces 46 chunks total. The two long
sections (Policy 02 §3 and Policy 05 §3) get split into 5 sub-chunks each.


================================================================================
src/embedder.py    "Turning text into numbers a computer can compare"
================================================================================

WHAT IT DOES
------------
Wraps a model called BAAI/bge-small-en-v1.5 from sentence-transformers.
This model turns any piece of text into a list of 384 numbers (a vector).

THE BIG IDEA
------------
Two pieces of text that MEAN similar things produce similar vectors.
"How often must we screen sanctions?" and "frequency of PEP checks" -
their vectors will be close together, even though the words are
different. This is how we do "semantic search."

THE LOGIC
---------
1. Lazy loading. We do NOT load the model when this file is imported.
   We only load it the first time someone calls .encode(). This means
   you can import this file in unit tests without paying the 2-second
   model-load cost.

2. Normalization. We force every vector to have a length of 1. This
   sounds technical but the reason is simple: when vectors are
   normalized, the FAISS inner product equals the cosine similarity.
   Cosine similarity is the standard way to compare "meaning."

3. We return a numpy float32 array because that's what FAISS wants.

WHY BGE-SMALL?
--------------
- It's free and open-source.
- It runs on a CPU (no GPU needed).
- 384 dimensions is small enough to be fast, big enough to be accurate.
- It scores well on the MTEB leaderboard (the standard benchmark for
  retrieval models).


================================================================================
src/vector_store.py    "The library of vectors on disk"
================================================================================

WHAT IT DOES
------------
Stores all the chunk vectors so that, given a new question vector, we
can quickly find the closest stored vectors.

We use FAISS, Facebook's library for vector search.

THE STRUCTURE
-------------
After ingest, the ./data folder contains three files:

  faiss.index    The FAISS index (binary file, the actual vectors)
  chunks.jsonl   One Chunk per line (the original text + metadata)
  meta.json      Just stores the vector dimension and count for sanity
                 checking on load

We use IndexFlatIP. "Flat" means it's a brute-force index - it compares
the query against every stored vector. With only 46 chunks this is
instant. With millions of chunks we'd use IVF or HNSW, but Flat is exact
(no recall loss) and dead simple to debug.

Simple Analogy

Flat Search
Find a person in city
↓
Check every house

Accurate but slow.

IVF
Go to likely neighborhood first

Faster but may miss someone.

HNSW
Ask people who know nearby people
until you reach the target

Very fast and usually accurate.

THE METHODS
-----------
- add(): append new vectors and their corresponding Chunks.
- search(): given a query vector, return the top k most similar chunks
  with their scores.
- persist(): write everything to disk.
- load(): read everything back from disk.

WHY WE STORE chunks.jsonl ALONGSIDE
-----------------------------------
FAISS only knows about vectors. It returns row numbers like "rows 7, 22,
31 are the closest." We need to map those row numbers back to the actual
chunk text. chunks.jsonl is that map. The order of lines in chunks.jsonl
exactly matches the row order in faiss.index.


================================================================================
src/retriever.py    "Finding the right chunks for a question"
================================================================================

WHAT IT DOES
------------
Given a question, returns the top k chunks most likely to contain the
answer. Uses TWO different methods and combines them.

THE TWO METHODS
---------------
1. DENSE retrieval (semantic): we embed the question, then ask FAISS for
   the closest chunk vectors. Good at finding chunks that MEAN the same
   thing as the question, even if the words are different.

2. SPARSE retrieval (BM25): a classic keyword-matching algorithm. Good
   at finding chunks that contain the EXACT words from the question.

WHY BOTH?
---------
Compliance policies are full of specialized terminology: "PEP", "EDD",
"MLRO", "SDD", "Section 4". Dense embeddings sometimes blur these rare
words into similar concepts and miss the exact policy. BM25 nails them
because it cares about exact word matches.

But BM25 alone fails on paraphrases: ask "how often must screening be
repeated" and BM25 won't match a chunk that says "frequency of checks"
- no shared rare words. Dense embeddings handle that case fine.

Combining both gives us coverage on both styles of question.

THE FUSION: RECIPROCAL RANK FUSION (RRF)
----------------------------------------
We can't just add the scores from dense and BM25 - they live on totally
different scales. So we use RRF, which only looks at RANKS, not raw
scores. The formula is:

    score(chunk) = sum over each list of (1 / (60 + rank))

Where rank is the chunk's position in that list (0, 1, 2, ...).
A chunk that ranks #1 in dense AND #1 in BM25 gets the highest combined
score. A chunk that only appears in one list gets a smaller boost.

We then take the top k from the fused list and return them.

THE LOGIC, STEP BY STEP
-----------------------
1. Tokenize the question (lowercase, split into words).
2. Run dense search: get top 20 chunks from FAISS.
3. Run BM25 search: get top 20 chunks from BM25.
4. For every chunk that appeared in either list, compute its RRF score.
5. Sort by RRF score, take top k.
6. Return as RetrievedChunk objects (chunk + final score).


================================================================================
src/prompts.py    "What we say to the LLM"
================================================================================

WHAT IT DOES
------------
Holds the text we send to the LLM. There are three prompts:

1. SYSTEM_PROMPT - the rulebook. Sent every time. Tells the LLM:
       - Only use the chunks I give you. No outside knowledge.
       - If the chunks don't have the answer, say so. Don't make things
         up. Point to the escalation procedure (MLRO).
       - Don't invent section numbers or policy names.
       - Reply with JSON in this exact shape: { "answer": "...",
         "used_chunk_ids": [...] }

2. build_user_prompt() - builds the actual question message. It formats
   each chunk like:
       [CHUNK 7]
       Document: 02_source_of_wealth.md | Section: 3.1 ...
       Required documents: ...
   Then appends the user's question at the bottom.

3. REPAIR_SYSTEM_PROMPT - used as a SECOND attempt if the LLM's first
   reply was broken JSON. Says: "your last reply was bad, return ONLY
   the JSON object, no extra text, no markdown."

WHY THE STRICT RULES IN THE SYSTEM PROMPT
-----------------------------------------
Without these rules the LLM will sometimes:
- Use its training data instead of the chunks (hallucination).
- Invent a plausible-looking policy section that doesn't exist.
- Refuse to refuse: when the chunks don't contain the answer, it makes
  one up anyway.

The system prompt is our main weapon against all three. It's what makes
us pass Q5 (the cryptocurrency question that has no answer in the docs).

WHY ASK THE LLM FOR CHUNK IDS, NOT FULL CITATIONS
-------------------------------------------------
Big trick: we tell the LLM "give me a list of integer chunk IDs you
used." Then in query.py we build the citation objects OURSELVES from
those IDs by looking up our own retrieved chunks.

This means it is structurally impossible for the LLM to invent a fake
citation. The only chunks that can end up in the citations field are
chunks we actually retrieved. If the LLM gives us a chunk ID we didn't
send it (it sometimes does), we drop it.


================================================================================
src/llm.py    "Talking to the language model"
================================================================================

WHAT IT DOES
------------
A thin wrapper around two possible LLM providers: Groq (default) and
Ollama (local). Both expose the same generate_json() method, so the
rest of the code doesn't care which one is being used.

THE LOGIC
---------
LLMProvider is an abstract base class with one method: generate_json().
Two concrete classes implement it:

- GroqProvider: uses the official `groq` Python package. Calls Groq's
  chat-completions API with response_format={"type": "json_object"}.
  This tells the server "the model MUST return valid JSON, not prose."

- OllamaProvider: uses Python's built-in urllib to POST to a local
  Ollama server (http://localhost:11434/api/chat). Uses format="json"
  which is Ollama's equivalent.

build_provider() looks at the LLM_PROVIDER env var and returns the
right one.

ERROR HANDLING
--------------
Every failure (network down, invalid JSON, wrong API key) is wrapped
in a single LLMError exception. The query orchestrator catches ONE
exception class and decides what to do. Simple and predictable.

WHY GROQ?
---------
- Free tier with very generous limits.
- Llama 3.3 70B is a high-quality model good at reasoning AND refusal.
- Sub-second latency.
- Native JSON mode (the model is forced to produce valid JSON).

WHY KEEP OLLAMA AS A FALLBACK
-----------------------------
For reviewers who don't want to sign up for a Groq key, they can run a
local model. Same interface, just slower and slightly worse on the
hardest questions.


================================================================================
src/ingest.py    "The conductor for the ingest pipeline"
================================================================================

WHAT IT DOES
------------
Wires together chunker + embedder + vector_store into one function:
run_ingest(policies_dir, settings).

THE LOGIC
---------
1. Call chunk_corpus(policies_dir) to get all 46 chunks.
2. Create the embedder.
3. Extract the .text from every chunk into a list.
4. Call embedder.encode() to get all 46 vectors at once.
5. Create a VectorStore with the right dimension.
6. Add all vectors + chunks to the store.
7. Persist the store to disk.
8. Return a summary dict (chunks count, docs count, etc.) so main.py
   can print it.

WHY KEEP IT SEPARATE FROM main.py
---------------------------------
main.py is just the CLI layer. The actual logic lives here so it can be
called from a test, a script, or a different CLI without rewriting.


================================================================================
src/query.py    "The conductor for the query pipeline"
================================================================================

WHAT IT DOES
------------
The most important file in the project. Takes a question, runs the
whole RAG pipeline, returns a QueryResponse.

THE LOGIC, STEP BY STEP
-----------------------
1. Start a timer (so we can report latency_ms at the end).

2. Load the vector store from disk. If it doesn't exist (user didn't
   run ingest), return an error response and write to audit.log.

3. Build the embedder and the hybrid retriever. Get the top k chunks
   for the question.

4. Build the LLM provider. If GROQ_API_KEY is missing, return an
   error response.

5. Build the user prompt using prompts.build_user_prompt() and call
   the LLM. Pass through _call_llm_with_repair() which:
       a. Tries the normal SYSTEM_PROMPT.
       b. If the response doesn't validate against LLMAnswer, tries
          again with the REPAIR_SYSTEM_PROMPT.
       c. If THAT fails too, raises LLMError.

6. Take the used_chunk_ids the LLM returned. For each one:
       - If it matches a chunk we actually retrieved, build a Citation.
       - If the LLM made up an ID, drop it and warn to stderr.
       (This is the anti-hallucination trick.)

7. Stop the timer, compute latency_ms.

8. Build the final QueryResponse with answer, citations, model name,
   latency, timestamp.

9. Write everything to audit.log via _safe_audit().

10. Return the QueryResponse.

WHY EVERY ERROR PATH BUILDS THE SAME RESPONSE SHAPE
---------------------------------------------------
The brief is explicit: even on failure, stdout must be a valid JSON
object matching the schema. So we have a helper _error_response() that
builds a QueryResponse with empty answer, empty citations, and the
`error` field filled in. The user / test runner ALWAYS sees the same
shape and can rely on it.

WHY _safe_audit() WRAPS THE WRITE IN A try / except
---------------------------------------------------
The audit log is important, but if disk is full and we can't write,
we shouldn't crash the user's query. We log the failure to stderr and
keep going. (In a production system you'd probably page someone.)


================================================================================
src/audit.py    "Writing the audit log"
================================================================================

WHAT IT DOES
------------
One function: write_audit_entry(path, entry). Appends one line of JSON
to audit.log.

THE LOGIC
---------
- Open the file in append mode ("a").
- Write entry.model_dump_json() followed by a newline.
- Done.

WHY APPEND-ONLY
---------------
A compliance audit log should NEVER be edited. If you could rewrite
history, the audit would be useless. Append-only means every past
query stays exactly as it was recorded.

WHY JSON LINES (NOT ONE BIG JSON ARRAY)
---------------------------------------
JSON Lines format = one JSON object per line. Two benefits:
- We can append to the file without re-reading the whole thing.
- A single corrupted entry doesn't break the rest of the file.
- Standard log-analysis tools (grep, jq, Splunk, etc.) can process it
  line by line.


================================================================================
main.py    "The command-line interface"
================================================================================

WHAT IT DOES
------------
The single file the user runs. Defines two commands using Typer:

  python main.py ingest --docs <path>
  python main.py query --question "<text>" [--k <number>]

THE LOGIC
---------
1. At the top of the file, we set some environment variables BEFORE
   importing any heavy libraries. These silence noisy warnings from
   HuggingFace and the tokenizers library. We want stdout to be ONLY
   the JSON response, no extra noise.

2. We compute PROJECT_ROOT as the folder where main.py lives, and
   AUDIT_PATH as PROJECT_ROOT/audit.log. This way no matter where
   the user runs the command from, the audit log always lands in the
   same place (next to main.py).

3. @app.command() decorators define the two commands. Typer reads the
   function signature and builds the CLI flags automatically.

4. For `ingest`: call run_ingest, print the summary JSON, done.

5. For `query`:
       a. Call run_query (which does ALL the work).
       b. Print response.model_dump_json() to stdout.
       c. If anything bubbles up unhandled (it shouldn't, but just in
          case), print a last-resort error JSON. This means stdout is
          GUARANTEED to be valid JSON, no matter what.

WHY TYPER
---------
- Clean syntax: just decorate a function.
- Free --help text.
- Type-safe argument parsing (the int conversion for --k is automatic).
- Tiny dependency.


--------------------------------------------------------------------------------
PART 4. THE 4 BIG DESIGN DECISIONS (and why)
--------------------------------------------------------------------------------

These are the same Decision Records that appear in the README, but
explained in simpler English.


DR-1. HYBRID RETRIEVAL (dense + BM25), NOT JUST DENSE
-----------------------------------------------------
Pure semantic search (dense embeddings) is great at understanding
meaning, but it can miss exact-word matches like "PEP" or "Section 4.1".
Pure keyword search (BM25) is great at exact matches but bad at
paraphrases.

Using both and fusing them with RRF gives us the strengths of both with
basically no downside (BM25 is essentially free to compute).


DR-2. SECTION-ALIGNED CHUNKS, NOT FIXED-SIZE CHUNKS
---------------------------------------------------
Most RAG tutorials say "split every 500 characters with 50 character
overlap." That works for blog posts. It does NOT work for legal /
compliance text, where each section is a self-contained rule.

By splitting on the `##` headings in the markdown, every chunk is
exactly one rule. The citation we show the user is exactly the rule
the answer is based on. Much easier to audit.


DR-3. GROQ LLAMA 3.3 70B AS THE DEFAULT
---------------------------------------
We needed an LLM that is:
- Free or very cheap (this is an open-source project).
- Good at multi-step reasoning (Q3 about PEP + risk score 72).
- Good at REFUSING when the answer isn't in the documents (Q5 about
  cryptocurrency).
- Supports a "must return JSON" mode (so we don't waste calls on
  unparseable responses).

Groq's free tier checks all four boxes. Llama 3.3 70B is a strong model.
Latency is under a second once the model is warm. We fall back to Ollama
for fully offline use.


DR-4. CITATIONS BUILT FROM CHUNK IDS, NOT FROM LLM TEXT
-------------------------------------------------------
This is the most important anti-hallucination trick in the project.

If we asked the LLM "return a list of citations as text", it would
sometimes invent citations - confident-looking quotes from policy
sections that don't exist. Catastrophic for a compliance product.

Instead we tell the LLM "return only INTEGER chunk IDs you used."
Then in query.py, we look up each ID in our own retrieved list and
build the Citation objects ourselves.

Result: a fabricated citation is structurally impossible. The only
chunks that can appear in the response are chunks we actually showed
the LLM and retrieved from our own data.


--------------------------------------------------------------------------------
PART 5. END-TO-END WALKTHROUGH OF ONE QUERY
--------------------------------------------------------------------------------

Let's trace exactly what happens when the user runs:

  python main.py query --question "How often must sanctions screening be repeated for medium-risk clients?" --k 3

STEP 1. main.py wakes up.
        Sets env vars to silence warnings.
        Typer parses --question and --k.
        Calls run_query() from src/query.py.

STEP 2. query.py starts a timer.

STEP 3. query.py calls VectorStore.load("./data").
        Reads faiss.index, chunks.jsonl, meta.json from disk.
        Now we have 46 chunks and their vectors in memory.

STEP 4. query.py builds the Embedder (which loads BGE-small from cache)
        and the HybridRetriever (which builds a BM25 index over the
        46 chunks - happens once, fast).

STEP 5. retriever.retrieve(question, k=3) runs:
            a. Encode the question into a 384-number vector.
            b. FAISS finds the 20 closest chunk vectors.
            c. BM25 finds the 20 chunks with the most matching words.
            d. RRF combines the two rankings.
            e. Returns the top 3.

        For our question, the top 3 are all chunks from
        03_sanctions_and_pep_screening_procedure.md, including the
        "Ongoing Periodic Screening" section.

STEP 6. query.py builds the GroqProvider (uses GROQ_API_KEY from .env).

STEP 7. prompts.build_user_prompt() formats a message:
            CONTEXT CHUNKS:
            [CHUNK 17]
            Document: 03_sanctions_and_pep_screening_procedure.md | Section: 4. Ongoing...
            ...

            [CHUNK 18]
            ...

            [CHUNK 19]
            ...

            QUESTION:
            How often must sanctions screening be repeated...

STEP 8. query.py sends the SYSTEM_PROMPT + user prompt to Groq.

        Groq returns roughly:
            { "answer": "For medium-risk clients, sanctions screening must
              be repeated quarterly.", "used_chunk_ids": [17] }

STEP 9. query.py validates this against LLMAnswer. It parses fine, no
        repair needed.

STEP 10. query.py looks up chunk_id 17 in the retrieved list. It exists.
         Build a Citation with the document name and the chunk text.

STEP 11. query.py stops the timer. latency_ms = ~22000 (most of this is
         the cold-start of BGE on a fresh subprocess).

STEP 12. query.py builds the final QueryResponse:
             question: "How often must sanctions screening..."
             answer:   "For medium-risk clients, sanctions screening
                        must be repeated quarterly."
             citations: [{ document: "03_sanctions...", chunk: "..." }]
             model:     "llama-3.3-70b-versatile"
             latency_ms: 22722
             timestamp: "2026-05-16T08:14:34Z"
             error:     null

STEP 13. query.py calls _safe_audit(). One line is appended to audit.log
         containing: the question, the response we just built, the
         exact 3 chunks we sent to the LLM, the model name, the
         latency, the timestamp.

STEP 14. main.py prints response.model_dump_json() to stdout.

STEP 15. The user sees the JSON. The shell exits.

         Total time on the user's machine: about 22-25 seconds.


--------------------------------------------------------------------------------
PART 6. WHY THIS DESIGN PASSES THE TRICKY TEST CASES
--------------------------------------------------------------------------------

Q3 (multi-document reasoning): a client is a PEP AND scores 72.
    Why we get it right: hybrid retrieval pulls chunks from multiple
    policies (CDD + Sanctions/PEP). The LLM sees both sets of rules
    and correctly identifies that EITHER trigger is enough for EDD.

Q4 (nuanced lookup): a passport expired 4 months ago.
    Why we get it right: section-aligned chunking keeps the
    "passports expired within 6 months" rule AND the "issued within
    10 years" rule in the same chunk (they're in the same section).
    The LLM sees both rules together and applies them correctly.

Q5 (cryptocurrency, NOT in the docs):
    Why we get it right: the SYSTEM_PROMPT explicitly says "if the
    context doesn't contain the answer, say so and point to the MLRO
    escalation path." The LLM refuses honestly instead of making up
    a procedure. The retriever still pulls the relevant "escalate to
    MLRO" chunk because it semantically matches "wealth source not
    covered." The LLM uses that chunk to explain its refusal properly.

PART 7. HOW EVERY DEPENDENCY EARNS ITS PLACE
--------------------------------------------------------------------------------

typer                 CLI. Cleaner than argparse, smaller than Click.
pydantic              Data shapes + validation. Required by the brief.
pydantic-settings     Reads .env into a Settings object.
python-dotenv         Loads .env into environment variables.
sentence-transformers Embedding model (BGE-small). Free, local, CPU-only.
faiss-cpu             Vector index. Fast, local, no server needed.
rank-bm25             Keyword search for the hybrid retriever.
numpy                 Array math, required by FAISS.
groq                  Official Groq API client.


--------------------------------------------------------------------------------
PART 8. WHAT WE DELIBERATELY DID NOT USE (and why)
--------------------------------------------------------------------------------

LangChain / LlamaIndex
    These frameworks hide too much. For a 5-document corpus we want
    full control over chunking, prompting, and validation. Hiding
    those behind abstractions makes debugging painful and makes the
    code harder to audit (which is the whole point of this project).

FastAPI
    The brief is a CLI tool. Adding HTTP would be extra surface area
    to test and maintain for no benefit.

A re-ranker (cross-encoder)
    Over 46 chunks the marginal benefit is small. Worth adding only
    if the corpus grew to thousands of documents.

A cloud database (Pinecone, Weaviate, etc.)
    The brief explicitly says local persistence is fine. FAISS is
    simpler, faster (no network), and free.
